# Internal Cryptographic Audit — 2026-10-14

**Scope:** hand-written, std-only, zero-dependency crypto primitives in
`~/workspace/native-core-draft/core/src/crypto/` and their protocol consumers.

**Auditor:** internal (Sentinel build system). **This is NOT an independent
professional audit.** Nothing in this report makes the crypto production-ready.
An independent audit by qualified cryptographers is still mandatory before
real money, real identities, or adversarial deployment.

## Methodology

1. Read every line of each primitive implementation.
2. Checked test vectors against the RFCs (Ed25519: RFC 8032 §7.1 tests 1–3;
   ChaCha20-Poly1305: RFC 8439 §2.8.2; X25519: RFC 7748 §6.1;
   SHA-512: FIPS 180-4 examples).
3. Traced nonce/IV discipline, entropy sources, and key lifecycle at every
   call site.
4. Wrote and ran an actual small-subgroup forgery against `ed25519::verify`
   to confirm exploitability before fixing.
5. Ran the full workspace suite after the fix (601 passed, 0 failed,
   0 warnings).

## Findings

### HIGH-1 (FIXED): Ed25519 `verify()` accepted small-order public keys

**What:** `verify()` rejected the identity point but accepted other
low-order points (order 2, 4, 8). The verification equation is the
non-cofactored `[S]B − [k]A == R`. For a small-order `A`, an attacker
holding no secret can forge a signature in a handful of hash tries:
pick random `s`, try `t` in `0..order` with `R = [s]B − [t]A`, keep the
`t` matching the equation. Demonstrated working in
`small_order_forgery_is_blocked` — the forged `(R, S)` satisfies the raw
equation.

**Exploitability in TRV's protocols:** limited. All honestly generated keys
are full-order, and identity keys are pinned out-of-band, so an attacker
could only forge signatures under a small-order key they themselves
published. Still, the primitive was weaker than its contract, and
fail-closed is the house rule.

**Fix:** `verify()` now rejects any public key with `[8]A == identity`
(one scalar multiplication, negligible cost). Non-canonical `S` was
already rejected; non-canonical point encodings were already rejected in
`ge_frombytes`. Regression tests added (order-2 torsion point rejected;
live forgery constructed and confirmed blocked).

### MEDIUM: no independent professional audit exists

Stated in every module's docs and repeated here: vector-tested is not
audited. Hand-rolled field arithmetic, scalar reduction, and ladder code
are exactly the class of code where subtle bugs survive testing. **Do not
ship production value on this until an independent audit happens.**

### LOW-1: `ed25519::SecretKey::hex()` exposes seed hex

By design for issuer tooling (`cli keygen` prints it with KEEP SECRET
warnings). Footgun if misused; documented. No change.

### LOW-2: messaging uses handshake-ephemeral keys, not per-message ephemerals

`messaging.rs` runs over `transport::Channel` (ephemeral X25519 per
handshake, HKDF'd session keys, sequence-bound nonces). There is no
per-message ratchet (Signal-style). Forward secrecy is per-handshake.
Noted as a design boundary, not a bug.

### INFO: mail.rs sender identity is self-asserted

The inner Ed25519 signature verifies against the key claimed inside the
sealed box; there is no PKI binding username → key (acknowledged as future
work). The signature proves the message came from the holder of the
claimed key, nothing more.

## Verified good

- **Ed25519:** RFC 8032 test vectors 1–3 pass (sign + verify, exact bytes).
  Deterministic nonce per RFC 8032 §5.1.6. Scalar clamping correct.
  Non-canonical `S` rejected (malleability). Identity point rejected.
  Point decompression checks canonical encoding, quadratic residuosity,
  and curve membership. Secret keys zeroized on drop; `Debug` redacted.
- **ChaCha20-Poly1305:** RFC 8439 §2.8.2 vector passes (ciphertext and the
  RFC's published tag). Tag verified in constant time BEFORE decryption;
  no plaintext on failure. Poly1305 `r` clamped at the byte level per RFC.
  One-time key wiped after use.
- **X25519 (`transport.rs`):** RFC 7748 §6.1 vector passes. Scalar clamping
  correct (`e[0] &= 248; e[31] &= 127; e[31] |= 64`). Peer point bit 255
  masked on decode. Low-order points rejected via exact order probe
  (`is_low_order`); all-zero peer and all-zero shared secret rejected.
  Shared secret always HKDF-SHA512'd before use — never used raw.
  Montgomery ladder is constant-time in field ops (`fe_cmov` selection).
- **SHA-512:** FIPS 180-4 vectors pass (empty, "abc", 112-byte multi-block).
  Correct padding, initial state, round constants.
- **PBKDF2:** 600,000 iterations for the vault (conservative; OWASP
  recommends ≥210k for HMAC-SHA512). Fresh random 16-byte salt per save.
  Salt/nonce/params bound into the AEAD as associated data.
- **Nonces:** transport uses 4-byte random session prefix + 8-byte sequence
  (never repeats; exhaustion fails closed at `u64::MAX`). Mail uses a fresh
  random nonce per email under a fresh per-email key. Vault and history use
  fresh random nonces per write. No nonce reuse found anywhere.
- **Entropy:** all key/nonce/salt generation reads `/dev/urandom` and fails
  closed (`EntropyUnavailable`) with no weak fallback.
- **Key hygiene:** `SecretKey` zeroized on drop (both wrappers); `Channel`
  wipes session keys on drop; `mail::seal`/`open` wipe ephemeral, shared
  secret, and symmetric key; HMAC/PBKDF2 wipe pads and chaining values.
  `Debug` impls redact secrets. Error types carry reason codes only — no
  key material in errors or logs. All encryption call sites use the
  authenticated `encrypt`/`decrypt`; no unauthenticated encryption found.
- **Transport channel:** per-direction keys + AAD labels (no reflection);
  64-entry replay window marked only after tag verification; coarse errors.

## What was fixed in this audit

1. `core/src/crypto/ed25519.rs` — `verify()` rejects small-order public
   keys (`[8]A == identity` check). 2 new regression tests, one of which
   constructs a working forgery and proves it is now blocked.
2. This report: `core/src/crypto/AUDIT-2026-10-14.md`.

## What remains

- Independent professional cryptographic audit (mandatory before production).
- Per-message ratchet / post-compromise security for messaging (design decision).
- PKI or key-transparency binding for `username@rv.com` → identity key.
- The `hex()` seed-export API should be reviewed before any tooling ships.

## Bottom line

The primitives are carefully written, honestly documented, and now pass
this internal audit with one real bug found and fixed. **They are NOT
production-ready:** no independent audit has happened, and hand-rolled
elliptic-curve code is precisely where subtle vulnerabilities hide. Ship
test builds only until a professional audit is complete.
